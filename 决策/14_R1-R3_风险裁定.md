## 二、风险 R1：虚拟触觉毯入口空间尺度（含世界锚点）

> **状态：待裁定（用户指示先不处理）。**
> 证据来源：原 `15_R1_虚拟毯入口尺度_证据与裁定.md`（2026-09-28，裁定代理 R1，只读分析；未提交 git、未改任何生产代码或数据）。
> 前置：`11_T系列_方案.md` §4.1（原生毯契约）/ §4.3（V3 判据裁定）；T1 执行记录（C2 全量完成 140 session）。

### 1. 结论（原 R1 ①）

**建议方案：D —— 入口张量 (192, 96)（虚拟毯 320×120 直接 bilinear 到 192×96，长轴 ×2 分辨率）；待用户确认。**

理由（全部可复算，数值见 §3）：

1. **现行方案 A 的入口不是"同一物理场换分辨率"，而是入口像素被放大 2×**：长轴入口像素 41.667mm（原生 20.833mm），足印像素面积 **44.237 px² vs 原生 88.474 px² = 0.500000（精确一半）**；各向异性压缩 **2.6667 vs 原生 1.3333（恰好 2.00×）**，且足印在入口的像素纵横比从原生 1.50（沿行伸长）反转为 0.75（沿列伸长）。
2. **A 还附带一个纯信息丢失项（非尺度问题）**：320→96 的 bilinear 是 2×2 定点采样、步长 3.333，长轴 320 行中 **128 行（40.0%）永不参与入口任何像素**（解析 + one-hot 基双重验证）。S5091 实测：有压帧的入口非零像素 A 20.09 / B 24.62（**+22.5%**）。
3. **方案 B 按其字面描述达不到"与原生一致"**：只要入口是 96×96 且覆盖 4m，长轴入口像素必然是 4.0/96 = 41.667mm，足印必然是 5.76×7.68 px —— 与 A **逐项相同**。B 唯一真实收益是消除 40% 丢行（抗混叠）。B 的题面陈述（"入口像素物理尺寸与原生完全一致（2.083cm/px）、足印恢复 11.5×7.7px"）在 96×96 入口下**算术上不可能同时成立**（96 像素覆盖 4m 与覆盖 2m 互斥）。**这一点必须在拍板前更正，否则会造成"尺度问题已修复"的错误结论。**
4. **要把入口像素语义恢复成原生，只有两条路**：缩短视场（方案 C：2m 滑窗，代价高、需窗口位置信号）或提高入口分辨率（方案 D：192×96）。D 让 320×120→192×96 的降采样倍率（长 **1.6667**、宽 **1.25**）与原生 160×120→96×96 **完全一致**，于是入口像素尺寸、源像素/入口像素、足印像素、各向异性、以及 **每一层特征图的物理格距**（conv1→layer4，D：4.21/4.26/8.51/16.67/33.33 cm vs 原生：4.26/4.35/8.70/16.67/33.33 cm，比值 0.98–1.00）全部与原生对齐；唯一差异是**长轴视场 4m vs 2m**，这正是用户 09-28 裁定的虚拟毯本意。
5. **D 的代价可测且有限**：入口 H 96→192 只改 `image_pressure.py:130` 一行；模型结构零改动（resnet18 `AdaptiveAvgPool2d((1,1))` + `fc=Linear(512,2048)` 吸收任意 H×W，`FRAPPE.forward` 的 height/width 是运行时读取，GRU `input_size=2048` 不变，参数不变：触觉分支 12.218M / 全模型 200.31M）；实测前向 **触觉分支 +119.7%**（1176.8→2585.9 ms/320 图）、**整模型 +62.3%**（2300.2→3733.8 ms/步，B=16,T=20，CPU）。不需重产任何数据（140 session 落盘不动），V3 判据数值不受影响（§3-e）。
6. **若用户坚持"入口 96×96 不变"的既有裁定**：退守方案 B，但必须按 **消费端**实现（磁盘保持 (T,320,120)，在 `_resize_pressure` 内先 320×120→160×120 area 降采样再 bilinear 96×96），并**明确记录"入口尺度仍为原生的一半"**。题面所述"改 adapter 落盘侧、消费端零改动"的 B 变体**不可行**（见 §4 更正栏：会击穿 `image_pressure.py:177-180` 与 `test_virtual_carpet.py:390-399`，并把 V3 的 ±3px 窗口物理尺寸从 7.5cm 变成 15cm）。

**并行提示（优先于本裁定）**：虚拟毯的**世界锚点**目前把行走区域切掉了一半 —— 全量 140 session 中 **28,325/52,612 帧（53.8%）整幅毯为空**、**30/140 session 全空**；仅 11.4% 的 session 行走范围完全落在毯内（细节与数值见 §5-1）。该问题是数据可用性问题，量级远超入口尺度差异，建议独立裁定。

> 拍板权归用户。**待用户确认**：入口尺寸取 (192,96)（方案 D）还是维持 (96,96)（方案 A/B）；以及锚点问题是否同批裁定。

### 5. 根因与修复指向

#### 5.1 根因（一句话）

**图像 ↔ mocap 的逐帧配对整体偏 +9.5 帧（+237.5 ms @40 Hz）**：第 j 帧图像显示的是第 j−9.5 帧的 3D GT，即每帧图像被配到了"未来 0.24 s"的姿态。
**不是**轴、**不是**单位/尺度、**不是** R-t 链（这三者已被"静止帧 4.5 px + 五个控制组 IoU 0.000 + 尺度不变校验 179.5 cm"逐项排除）；**也不是适配器算术**（位精确复现、out_of_span 0、按 `frames.mocap_time_s` 精确取样）。偏差位置在**共享事实层的时钟对齐**（`frames.npz` 的 `mocap_time_s` / `session.json` 的 `offset_s`）。

#### 5.2 修复指向（一步可验）

| 项 | 内容 |
| --- | --- |
| 施加对象 | 第 j 帧的 mocap 取样子时刻前移 **237.5 ms**：`mocap_time_s[j] → mocap_time_s[j] − 0.2375` |
| 等价写法 | `offset_s` 由 **0.631612 → ≈0.869**（因为 `mocap_time_s = visual_time_s − offset_s`）；或判定图像时间戳偏晚、把 `visual_time_s` 后移 237.5 ms（同一配对修正） |
| 修正粒度 | **逐 session 一个标量即可**（段内恒定已验证：三段 +10.5/+10.0/+8.5） |
| 方向确认 | 重投影只能定出"配对差"，**不能判定两侧谁错**；方向须由独立同步源（同步拍手/击地事件/marker 事件）最终确认后再落盘 |
| 验证方法 | 复用本报告扫描：after-fix 目标为"帧级对齐偏移 ≤5 px 且 lag*≈0、行走帧逐关节中位 ≤~15 px" |

#### 5.3 影响面（全库，非个例）

这是**逐 session 残差**，不是单一常数：已知可修的 47 个 session 的 lag* 覆盖 **−17…+16 帧（−425…+400 ms）**，38 个 session 在 lag 0 已 ≤8 px。
**建议（待用户裁定）**：训练/正式评估前做一次**全库逐 session 重同步审计**（脚本可复用 `/tmp/r2-scratch/s15_multi.py` + `s18_wide.py`），把每 session 的 lag* 落表，再决定是修 `offset_s` 还是修 `visual_time_s`。
对下游的语义后果：图像分支（CLIFF 特征）与 GT 是逐帧配对（`image_pressure.py:237-247`），GT 超前 237.5 ms = 监督"抢跑"；按实测图像速度 3.4–13.1 px/帧，对应 **32–124 px** 的系统性错位。**只看 3D/压力自身的指标不受影响，图像条件类指标（视觉→运动、MJE/PVE 等）会系统性变差**；静止帧不受影响（4.5 px）。

#### 5.4 顺带观察（不构成缺陷，供裁定参考）

1. `keypoints.npy` 是 **24 关节全部落盘**，但原生消费端 `image_pressure.py:238` 取 `[:, :23]` —— 即**只用 0..22（含 L_hand），丢掉 23（R_hand）**，左右不对称；链路数据本身完整，属原生上游设计选择。
2. 原生 MotionPRO 链**完全不使用相机**（`gen_bbox.py` / `gen_image_feature.py` 只吃图像，`focal_length` 硬编码 608 走 CLIFF 约定），因此本裁定抓到的相机链问题**不影响原生链行为**，只影响"用图像做 2D 校验/评估"这一路。
3. 多人场景下 YOLOX / RTMPose 会串人：542 帧中 226 帧（41.6%）的点云不落在该帧检测框内（已用 gate 剔除）；这是原生链的数据质量侧面发现。

**结构性发现（本扫描最强单一信号，直接影响修法选择）**：修正量与 `offset_s` 系统性相关，不是逐 session 独立噪声：

- 回归（**良态子集** CI≤2 帧 & n≥120 & gate_frac≥0.20，n=51）：`lag_eff = +25.55 × offset_s − 8.97`（r = **+0.865**, R² = **0.749**, 残差 rms **4.35** 帧；CI +21.41…+29.70）。

#### 6.5 置信类定义与边界声明

**分类判据（在查看分类结果之前固定）**：

```
1) align0 <= 8 px                 -> A 已对齐
2) n_gate < 100 或 gate_frac<0.20 -> D 证据不足
3) gain = align0 - align* < 3 px  -> D 证据不足
4) lag 置信区间半宽 > 4 帧         -> D 证据不足
5) align* < 12 px                 -> B 可平移修复
6) 否则                            -> C 修不动
```

- 阈值沿用 R2 文档口径（8 px / 12 px），未为本轮结果调参。
- `align0` = lag 0 处的帧级对齐偏移中位（px）；`align*` = 扫描窗内最小值；`gain = align0 − align*`。
- 顺序有意义：**A 优先**——`align0 ≤ 8 px` 意味着已到 4.5 px 静态地板，无需任何平移，不论平坦曲线的 argmin 落在何处。

**边界声明（必须与结论同时引用）**：

1. **本扫描不判定"两侧谁错"**。重投影只能定出"配对差"（相对量），不能判定是 `visual_time_s` 偏晚还是 `mocap_time_s` 偏早。方向须由独立同步源（同步拍手 / 击地事件 / marker 事件）最终确认，**与 §5.2 同一限定**。
2. **lag 点估计精度有限**。82/140 个 session 的残差曲线在 ±3 帧内抬升 <2 px（平坦谷）。故 lag 的**方向与量级稳健**，但 ±2 帧内的小 lag 不可靠——这正是 `lag CI > ±4 帧 → D` 这条规则的来源。抽样分歧中 9/15 属"同一平坦谷内两个不同点"。
3. **IoU 法的判别力只有 51/140**。89 个 session 的 IoU 曲线近乎平坦（中位凸显度 0.013），IoU 法对其**没有**独立结论。引用 IoU 复核通过率时必须同时给出"可判别子集"筛选条件。
4. **IoU 法的已知失效模式**：对已对齐（A 类）session，IoU 峰可能落在 −15 帧附近（凸显得 0.02–0.05），但那个 lag **不能降低位姿残差**（3 个 A 类分歧中 1 个已证实为伪峰、2 个"都不明显更优"）。IoU 是**交叉检查**，不是主判据。
5. **"恒标量"未获严格证明**。5 个抽样的分段 span 中位 1.50 帧、3/5 ≤2 帧，但 2/5 出现 5.5 帧的**单调**漂移（S13072、S13093，均在 20260810/S13）。逐段恒定是近似，段内漂移需单独裁决后再决定实施粒度。
6. **D 类 48 个 session 的修正量不可用**。表中给它们的 `lag_eff` 仅供排序参考，**不得**直接写入 `offset_s`。它们的共同原因是**门控通过率低（多人串人）或曲线平坦**，属 2D 前端数据质量问题，需先解决跟踪再做时钟标定。
7. **C 类 4 个不是时钟问题**。IoU 独立复核与 RTMPose 一致（方向/量级都对），平移后残余 12–19 px 来自同 session 的 2D 串人；它们的门控通过率 26%–76%。**不应**用更大幅度的平移去"修"它们。

#### 7.1 结论摘要

1. **构造层缺陷成立且可量化**：压力原始 `t_us` 与 cam3 视频时钟**同源**（会话首端偏移中位 **+0.11 帧 = +3 ms**，IQR [−0.18, +0.42] 帧），因此 `resample_pressure` 丢弃 `t_us` 造成的畸变是**可避免的纯构造畸变**：全库压力被压缩中位 **+3.42%**（p90 +8.3%，最大 +27.7%），会话末端相位误差中位 **+10.08 帧（0.25 s）**，25/139 会话 > 20 帧。
2. **互相关在这条链上判别力不足**：±40 帧窗口内峰−次峰（显著度）中位仅 **0.018**，**112/139 会话 < 0.05**；20/139 峰值落在窗口边界，27/139 |lag| > 35 帧 → 任务书要求的 **±30 帧窗口对相当比例 session 不够用**。
3. **左右配对**：用"构造已证的压力↔视频对齐"（前 25% 段，lag≈0）做**不用动捕**的独立裁决（HALPE-26 2D 像素脚信号）→ **74/3 支持直配**（压力 L 脚 = 解剖左）；动捕侧同判据 **54/23 支持直配**。即**未发现左右互换**，但见 §7.6 边界声明（前端自身命名约定不可自证）。
4. **与 S1 的联合解释不闭合**：锚点 lag 处相关系数中位仅 **+0.14**（直配）/最大两配对数 **0.28**，远低于自由峰 **0.48**；把 S1 的 `lag_pt`/`lag_eff` 叠加到我的对齐上，反而使"与视频侧裁决的符号一致率"从 **38/48 降到 27/43–28/45** → S1 的 lag（在 SMPL/adapter 产物上测得）不能直接搬到"raw BVH ↔ 压力"链上使用（§7.5-5 给出线索，未裁定）。

#### 7.4 构造映射检查

**1. `pressure_48.npz` 的时间字段**：**不含任何 t_us/T 字段**。字段仅：`frame_id, left48, right48, valid, fake, unit, value_min, value_max, source_file_left, source_file_right, source_time_column, alignment_method`。其中 `source_time_column = "t_us"`、`alignment_method = "linear_values_nearest_quality_on_normalized_t_us"`、`unit = "source_sensor_units"`；`source_file_*` 指向 **washer 出货版** `work://data_pipeline/pressure_washer/final_fake_marked/<date>/<subj>/<rec>/pressure_{left,right}.csv`。

**2. 构造映射（`AnysoleWorkspace/tool/build_shared.py: resample_pressure`）**：

```
target = linspace(0, 1, n_frames)
x      = (times - times[0]) / max(times[-1] - times[0], 1.0)   # 逐侧独立归一化
value  = interp(target, x, values)                             # 逐列线性；valid/fake 用最近邻
```

→ 逐侧 `[0,1]` 归一化 = **把每侧各自的时间轴拉伸到共享网格的帧数**，绝对时长信息被丢弃；隐含假设"压力记录与视频窗口起止同步"。实测两条相关事实：**出货版 CSV 的时间列本身是合成均匀网格**（140/140 session 的 shipped CSV `diff(t_us) ≡ 25000 µs`，全库一致，无例外）；**出货版 CSV 的起点逐侧独立**（例：S5011 left t0 = 98945.0 µs vs right t0 = 57162.5 µs，而两侧原始 CSV t0 均为 15000）→ **shipped `t_us` 不是物理共同时基**，逐侧归一化可能正是为规避这一点而写；但代价是丢掉了可用的绝对时长。

**3. 绝对锚点（原始 t_us + jpeg 绝对本地钟，全库 139）**：`Δ(i) = [started_at_iso 当日秒 + raw_t_us(i)] − J(i)`，其中 `J(i)` = 第 i 帧对应的 cam3 jpeg 文件名时刻：

| 量 | min | p25 | 中位 | p75 | max |
|---|---|---|---|---|---|
| `Δ(0)`（帧） | −1.13 | +0.18 | **+0.84** | +1.40 | +7.69 |
| `Δ(n−1)`（帧） | −4.62 | +4.55 | **+10.09** | +17.29 | +51.06 |
| 线性拟合截距（帧） | −1.13 | +0.18 | **+0.84** | +1.40 | +7.69 |
| 线性拟合漂移（帧，整段） | −10.15 | +3.79 | **+9.44** | +16.42 | +49.68 |

- **首端一致**：Δ(0) 中位 +0.84 帧 ≈ **21 ms**（p25/p75 = +4.5/+35 ms）→ 压力记录仪与相机**共用同一挂钟**（若各自独立，Δ(0) 应均匀散布在秒量级）。这是"丢弃 t_us 可避免"的实证依据

- 旁证：cam3 jpeg 全量跨度同样超 `n/40`（+0.15…+1.08 s），与 §7.4-3 的相机帧率偏差一致

**5. 重采样跟随的是哪个时钟？** 跟随的是**共享网格（视觉侧）时钟**：每侧 `[0,1]` → 拉伸到 `n_frames`，即"视频窗口起止"；与动捕时钟无任何关系。而压力原始时基本身**就等于视频时钟**（§7.4-3 首端 +3 ms）→ 因此这条链上**唯一可修的错位就在构造层**；动捕时钟的偏差是另一条独立问题（S1 负责）。影响面：Step2Motion（压力输入 × BVH 监督）、AnySole（压力 × f6_soft 标签）、MotionPRO 虚拟地毯（动捕足位绘压力）——三者的压力侧都继承了 §7.4-3 的 3.4% 压缩与末端 0.25 s 相位误差。

#### 7.5 配对裁决与 S1 联合解释

**1. 差分信号（对共同时钟偏移不变，对配对翻转敏感）**：`u = pL − pR`，`w = (−hL) − (−hR) = hR − hL`：直配 ⇒ `u ≈ +w`（r > 0）；交叉 ⇒ `u ≈ −w`（r < 0）。全库自由峰 `|r_u|` 中位 **0.557**（p25 0.302 / p75 0.745）——差分信号本身信噪比良好。**但自由峰符号无判别力**：`−w(t+τ) ≡ w(t+τ+P/2)`，自由搜索总会找到正峰（实测 105 个 |r|>0.3 的会话里 104 个都是正号）→ 必须用**独立定标的 lag** 取符号。

**2. 独立定标：前段（构造已证的 lag≈0）**。构造锚点在**首端**精度最高（Δ(0) 中位 +0.84 帧，且该处漂移尚未累积）；取前 25% 帧，压力↔视频 lag ≈ 0（漂移贡献 ≤ 2.5 帧）——**该 lag 与周期性无关**。在此 lag 处：

| 判据 | 强判组 (|r|>0.4) | 直配 | 交叉 | 弱组 |
|---|---|---|---|---|
| **2D 视频侧**（HALPE-26 像素，**不用动捕**） | 68 | **65** | **3** | 24 |
| 同上，lag 固定 0 | 77 | **74** | **3** | — |
| 动捕侧（raw BVH 脚高） | 77 | 54 | 23 | — |

- 2D 信号构造：左右脚各自 `{踝15/16, 大趾20/23, 小趾21/24, 跟22/25}` 像素 y 均值，去线性趋势后取差 `w_v = yL − yR`；`u ≈ +w_v` ⇒ 直配
- **视频侧（唯一一条不经过动捕的链）给出 74/3 的强指向：压力 L 脚 = 解剖左**；动捕侧同向（54/23，噪声更大）
- 交叉检查：把 S1 的 `lag_pt`/`lag_eff` 叠加到 mocap 侧对齐后，与视频侧符号一致率由 **38/48 降到 27/43 / 28/45** → 叠加 S1 lag 变差（见下条）
- 早前抽查（S11031 frame 206 等"压力左与动捕右脚同相"）系 **lag≈0 的错位比较**所致，已被本条判据取代

**3. 动捕侧 L/R 的自身正确性（复核）**：用 S1 的 `sweep_lib`（只读）做 3D 重投影 vs HALPE-26 的像素中位误差：干净 gate 会话同侧明显胜出（S10101 **4.5 px vs 82.2 px**；S14011 **6.1 px vs 48.2 px**）→ 动捕 L/R 与 2D 前端的 L/R 命名一致；结合上条（前端 L = 解剖左，标准约定）→ 两条链共同支持"压力 L = 解剖左"。

**4. S1 联合解释：不闭合（关键负面结论）**。构造意义下应有 `lag_pm(i) = Δ(i)/dt + lag_vm`。取 S1 的 `lag_eff` 代入并对齐：

| 量 | 中位 |
|---|---|
| `lag_pm` 锚点（首 / 中 / 末） | −5.72 / +0.92 / +2.80 帧 |
| 锚点处直配 r | **+0.142**（p25 −0.154 / p75 +0.444） |
| 锚点处交叉 r | **−0.034** |
| 锚点处 max(直,交) | **0.279** |
| 同会话自由峰 r（对照） | **0.484** |
| 直配 − 交叉（锚点处） | +0.003（**完全不可分辨**） |

- 锚点 lag 处差分相关同样 ≈ 0（前 25% 段中位 +0.046；±半周期处 +0.379 / +0.143）→ **构造锚点无法把压力与动捕对齐**
- 逐 session 检查显示：自由峰常落在"锚点 ± 半周期"处（如 S7032 锚点 mid −8.56 处 r = **−0.665**，而锚点 ±25.5 处 +0.650/+0.657；S5081 锚点 −2.11 处 −0.384、锚点 −11 附近 ≈ 自由峰 −10.8 的 +0.638）→ 锚点与测量值之间的差异**量级恰为半周期**，无法据此判定谁错
- 结论：**在 ±30/±40 帧窗口内，压力↔动捕的绝对 lag 不可辨识**；`lag_pv = lag_pm − lag_vm` 的联合式在本数据上**不能闭合验证**

**5. 线索（未裁定，留给 T1/主会话）**：`gait` 侧 MotionPRO adapter 的 `model_inputs/.../keypoints.npy`（SMPL 24 关节，网格索引 i）与本案"raw BVH 在 `mocap_time_s` 上采样"的脚高信号，最佳相关出现在 **lag −3…−5 帧**（S5091 −4/+0.259；S14011 −3/+0.564；S7032 −4/+0.632；S11031 −5/+0.716；SMPL 侧 up 轴实测为 axis 1）。该值与 S1 的 `lag_eff` 中位 −5.5 / `lag_pt` 中位 −8.5 同量级 → **怀疑"S1 测的是 SMPL/adapter 产物 ↔ 视频"的 lag，与"raw BVH ↔ 视频/压力"的 lag 不是同一个量**。本案仅记录现象（J 侧脚高代理取得粗糙，未做精确论断）。

#### 7.6 边界声明（判别力与不可判定项）

1. **判别力（量化）**：±40 帧窗口内峰显著度中位 0.018、112/139 会话 < 0.05；20/139 峰在窗口端点；27/139 |lag| > 35 → 现行 ±30 帧窗口不足，且"±30 帧内唯一解"这一假设**不成立**。
2. **互相关只能确定"配对差异"，不能确定哪一侧错**：本报告的"直配"指**压力标签 L 与动捕/2D 标签 L 一致**；不能据此断定"压力标签错"或"动捕标签错"（若两侧同时互换，观测相同）。
3. **前端命名约定不可自证**：§7.5-2 的解剖侧归属依赖 HALPE-26 前端的 L/R 约定（标准 COCO/HALPE 约定，但本案无法用数据自证前端未整体互换）。若前端整体互换，则该条结论翻转为"交叉配"。
4. **周期性混叠**：步态周期 ≈ 38–50 帧时，"左右换边"与"半周期时钟偏移"观测等价；本案所有"lag"结论都受此限制，除非另有绝对锚点。
5. **jpeg 时间戳语义**：文件名 `3_HHMMSS.mmm.jpg` 为写入时刻（±1 ms 量化），非曝光时刻；若写入延迟系统性存在，Δ(i) 的**斜率**项会被高估。§7.4-3 的**首端**结论（Δ(0) ≈ +3 ms）不受此影响，**末端/压缩比**结论受此影响（方向：可能高估）。
6. **压力绝对时钟速率不可自证**：原始采样步长 ≈31–33 ms（≈32 Hz）而 `meta.json: software_trigger_fps = 30`；本案只能证明"首端与相机钟一致 + 跨度比网格长"，不能排除记录仪时钟本身的慢漂移。
7. **S12102**：valid 帧 = 0（`IndexError` 级空集），**跳过**，未纳入任何统计。
8. **二值路线可用性**：动捕 3 cm 下 60/139、1 cm 下 56/139 会话二值信号零方差 → 二值互相关在全库不可普遍使用。
9. **范围声明**：本案只测"压力↔动捕"；视觉↔动捕、视觉↔压力分别归 S1 与本案 §7.4。所有脚本在 `/tmp/s2-scratch/`，未改生产代码/数据，未 commit。
